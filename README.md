# Leadwise

Sales CRM and performance dashboard for a real estate brokerage. Staff capture leads by hand, from Excel or from Meta lead ads, assign them, call them, track follow ups and file a daily report, and the owner sees how every person, department and ad campaign is doing.

> **Portfolio demo.** Leadwise is a demo version of a custom internal CRM I built for a real company. It is published only for portfolio purposes and runs on seed data only: every person, phone number, project, campaign, call and figure is synthetic and comes from the seed script. No company data is included. The Meta lead sync is built in but is not connected in the demo, so Meta leads do not arrive in real time; the campaign leads you see were generated by the seed.

## What it does

**Leads**

* Views for Mine, Unassigned, Assigned to others (owner only) and All, with a project filter and a month or custom date range.
* Twelve stages from New to Closed or Lost. A lost lead needs a reason.
* Priority comes from the possession timeline (under 6 months is High, 6 months to 1 year is Medium, more than 1 year is Low) and can be changed by hand.
* Assign, pick up, reassign and bulk assign. A lead can have more than one person on it. Closed and lost leads are locked.
* Hand over moves every open lead from one person to another in one step.
* Phone numbers are compared on their last 10 digits, in the form and again on the server, so the same buyer is never entered twice.
* Every change is written to `lead_events` with who, when, the old value, the new value and the reason.

**Lead intake, calls and campaigns**

* Excel upload finds the name, phone, source and project columns on its own, even below a title row.
* Meta lead ads: every 15 minutes the API pulls new Facebook and Instagram lead form entries through the Graph API, skips leads it has already seen by Meta lead id or phone number, and logs a repeat enquiry on the existing lead instead of creating a duplicate. Paused campaigns are skipped.
* One shared intake path handles the form, Excel and Meta, so the duplicate rules are the same everywhere.
* Calling a lead from its card opens the dialer and logs the call. Employees see their own call log; the owner sees calls by person.
* Campaigns (owner only) shows leads, working, booked and lost per campaign with its conversion rate, and lets the owner pause or resume a campaign and connect or disconnect Meta.

**Performance**

* Each department has monthly KPI targets. A change applies from the chosen month onward and never rewrites earlier months.
* The daily report records attendance (present, half day, absent, weekly off) and what was achieved against each KPI and each running project goal.
* Score is achieved over target, capped at 100%. Grade A is above 80%, B is 50% to 80%, C is below 50%.
* Pacing compares progress with how much of the period has passed: on target, on track, at risk (75% of pace or better) or behind.
* Project goals have a date range, a reward and a leaderboard.

**Access**

* Owner sees the whole business. An employee sees their own leads, the unassigned leads in their projects, and their own performance. The API enforces this; the UI only reflects it.
* Sign in with email and password or Google. Google sign up is limited to addresses the owner has added.
* Changes reach every open dashboard within a second through a private Supabase Realtime channel.

## How it fits together

The React app signs in with Supabase Auth and sends the session token to the Express API on every request. The API checks the token, loads the `users` row, rejects inactive accounts, applies the visibility rules, and talks to Postgres with the service role key. After a lead changes it broadcasts `changed` on the private `leads` channel, and every open client refetches its leads.

The browser never writes to Postgres directly. The publishable key is used only for auth and Realtime.

The API runs TypeScript directly on Node 22.18 or newer, so it has no build step.

**Stack:** React 19, React Router 7, TanStack Query 5, Tailwind CSS 4, Vite 8, TypeScript 6, Express 5, Supabase (Postgres, Auth, Realtime).

## Running it locally

You need Node 22.18 or newer and a Supabase project.

**1. Database.** In the Supabase SQL editor run `backend/supabase/schema.sql`, then `backend/supabase/crm_schema.sql`. Then in the Supabase dashboard:

* Authentication > Hooks: set Before User Created to `public.gate_signups`.
* Authentication > Providers: turn on Google if you want it.
* Authentication > Users: add the owner and employee users yourself (tick Auto Confirm User), with the passwords you want. Put their emails in `DEMO_OWNER_EMAIL` and `DEMO_EMPLOYEE_EMAIL`.

**2. Environment.** Create `backend/.env` with the variables listed below. It is the only env file: the frontend reads it too, and only the values it maps reach the browser.

**3. Install, seed and start.**

```bash
cd backend
npm install
npm run seed
npm run dev
```

In a second terminal:

```bash
cd frontend
npm install
npm run dev
```

Open http://localhost:5173. When the `VITE_DEMO_*` variables are set, the login page shows the demo accounts.

The seed clears the CRM tables and generates about six months of data: leads with their history, projects, goals, KPI sets, attendance and daily reports. It is deterministic, so every run gives the same data relative to today.

## Environment variables

One file, `backend/.env`, serves both apps.

**Shared (API and web app)**

* `SUPABASE_URL` (required): project URL.
* `APP_NAME` (required): product name.
* `APP_TIME_ZONE` (required): IANA zone for business days, for example `Asia/Kolkata`.
* `PORT`: API port, 4000 when not set. In development the web app forwards `/api` to it.

**API only**

* `SUPABASE_SECRET_KEY` (required): service role key. Never reaches the browser.
* `ALLOWED_ORIGINS` (required): comma separated list of web origins allowed to call the API.
* `META_PAGE_TOKEN`: Meta page access token. Leave it unset for the demo; the Meta sync stays off and the Campaigns page says so.
* `META_FORM_IDS`, `META_AD_ACCOUNT`, `META_ADS_TOKEN`: optional. Limit the sync to these lead forms, and skip leads from campaigns that are no longer running.
* `DEMO_OWNER_EMAIL`, `DEMO_EMPLOYEE_EMAIL`: only used by the seed, to know which Auth user is the owner and which is the employee. The seed never changes their passwords.

**Web app only**

* `SUPABASE_PUBLISHABLE_KEY` (required): publishable key.
* `CONTACT_EMAIL` (required): privacy contact.
* `VITE_API_URL`: full URL of the API, for example `https://api.example.com/api`. Leave it unset when the web host forwards `/api` to the API.
* `API_PROXY_TARGET`: local development only. Overrides where Vite forwards `/api` (default `http://localhost:<PORT>`).
* `VITE_DEMO_OWNER_EMAIL`, `VITE_DEMO_EMPLOYEE_EMAIL`, `VITE_DEMO_PASSWORD`: show the demo panel on the login page. Leave them unset in production.

A host that builds the web app on its own can set `VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY`, `VITE_APP_NAME`, `VITE_APP_TIME_ZONE` and `VITE_CONTACT_EMAIL` directly instead.

`npm run build` in `frontend` stops with a clear message if a required variable is missing. The API does the same at start up.

## API

Every endpoint except `GET /api/health` needs `Authorization: Bearer <supabase token>`. Errors come back as `{ ok: false, error }` with a matching status code. Unexpected server errors are logged on the server and return a generic message, never internal details.

* `GET /api/health`: database check and latency. Public.
* `POST /api/leads/list`: leads visible to the caller, with history, the roster and the months that have data.
* `POST /api/leads/import`: add up to 500 leads and report the ones already in the CRM.
* `POST /api/leads/write`: `update`, `assign`, `take`, `handover`, or `delete` (owner only). Employees can only change leads they are on.
* `POST /api/projects/list`: projects, members, goals and goal leaderboards.
* `POST /api/projects/write`: create, edit or delete projects and goals (owner), or file goal progress (members).
* `GET /api/performance/months`: months that have performance data.
* `POST /api/performance/summary`: scores, grades, KPIs and attendance. Employees only get their own.
* `POST /api/performance/reports`: file the daily report.
* `POST /api/performance/kpis`: save a department's KPIs from a month onward (owner).
* `POST /api/users`: create, update or delete users (owner).

## Deploying

**Database.** Run both SQL files on the production Supabase project, set the Before User Created hook, and add the production web address to the Auth redirect URLs.

**API.** Any Node host (Render, Railway, Fly.io, a container). Install with `npm install`, start with `npm start`, and set the backend variables. `ALLOWED_ORIGINS` must include the production web origin. The server finishes open requests before exiting on SIGTERM, and `GET /api/health` works as a health check.

**Web app.** Any static host. Set the web app variables (the `VITE_*` names when there is no `backend/.env`), run `npm run build`, and publish `dist`. Route every path that is not a file to `index.html` so deep links work. Either forward `/api` to the API on the same domain, or set `VITE_API_URL` to the API address before building.

Before going live, leave the `VITE_DEMO_*` variables unset and set a real `VITE_CONTACT_EMAIL`.

## Upgrading existing data

The seed and the possession options no longer use dashes in any text people see. For demo data, run `npm run seed` again. For real data, the possession option "6 months to 1 year" used to be written with a dash, and existing leads keep the old text until you run:

```sql
update public.leads set possession = '6 months to 1 year' where possession like '6 months _ 1 year';
```
